# Coding Guidelines

This repo is a **vendored/forked third-party library** — a Go port of Google's [libphonenumber](https://github.com/google/libphonenumber), forked from [nyaruka/phonenumbers](https://github.com/nyaruka/phonenumbers). Upstream conventions apply throughout; Accompany-specific changes are the exception, not the rule. See [docs/local-development.md](docs/local-development.md) for the upstream-sync workflow and the "Version Numbers" note in [README.md](README.md).

## Prefer syncing from upstream over hand-patching bugs

BAD — fixing a parsing bug by patching logic directly in this repo without checking upstream first:

```go
// "Fixed" a false-negative in isViablePhoneNumber by tweaking it locally.
```

GOOD — confirm the bug exists in [nyaruka/phonenumbers](https://github.com/nyaruka/phonenumbers) and/or [google/libphonenumber](https://github.com/google/libphonenumber) first (see [docs/troubleshooting.md](docs/troubleshooting.md)); if it's already fixed upstream, merge that commit instead of re-deriving the fix locally. Only hand-patch when the fix is Accompany-specific and has no upstream equivalent, and call that out explicitly in the PR description.

## Never hand-edit generated files

BAD:

```go
// Editing phonenumber.pb.go or phonemetadata.pb.go by hand to add a field.
```

GOOD: these files are headed `// Code generated by protoc-gen-go. DO NOT EDIT.` Change the `.proto` source (`phonenumber.proto`, `phonemetadata.proto`) and regenerate. The same applies to the gzipped files under `data/` — regenerate via `cmd/buildmetadata`, never edit the blobs directly.

## Keep upstream's constant-naming style for ported enums/constants

BAD — renaming a ported constant to idiomatic Go CamelCase, diverging from upstream and making future merges harder:

```go
const RegionCodeForNonGeoEntity = "001"
```

GOOD — match upstream's existing style so diffs against `nyaruka/phonenumbers` stay mergeable:

```go
const REGION_CODE_FOR_NON_GEO_ENTITY = "001"
```

New, Accompany-authored code that has no upstream equivalent should still follow idiomatic Go naming (`MixedCaps`, not `SCREAMING_SNAKE_CASE`) — this rule is only about not renaming things that exist to stay in sync with upstream.

## Errors: use predeclared `var ErrXxx` sentinels, not ad hoc `errors.New` at the call site

BAD:

```go
func Parse(number, region string) (*PhoneNumber, error) {
	if number == "" {
		return nil, errors.New("number too short")
	}
	...
}
```

GOOD — this repo declares package-level sentinel errors near the code that returns them (`ErrNumTooLong`, `ErrTooShortAfterIDD`, `ErrEmptyMetadata`, etc.) so callers can compare with `errors.Is`:

```go
var ErrNumTooLong = errors.New("the string supplied is too long to be a phone number")

func Parse(number, region string) (*PhoneNumber, error) {
	if len(number) > maxInputStringLength {
		return nil, ErrNumTooLong
	}
	...
}
```

## Scope changes to match the "strict port" goal

Per the `README.md` notice: don't add functionality that doesn't exist in upstream libphonenumber. If a service needs behavior beyond what this library offers, build that in the consuming service, not here — this keeps the fork mergeable with upstream indefinitely.

## Tests

Follow the existing table-driven test style in `phonenumbers_test.go` / `shortnumber_info_test.go`. When a test starts failing after a metadata refresh (`cmd/buildmetadata`), check whether the expected value itself is stale before assuming the code is wrong — see [docs/troubleshooting.md](docs/troubleshooting.md#test-failures-after-a-metadata-update).
